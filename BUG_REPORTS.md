# Bug Reports — NewsAppDemo

Все баги ниже найдены через статический анализ исходного кода и подтверждены
автоматизированными тестами-регрессионерами (см. столбец "Regression test").
Каждый баг воспроизводим в текущей версии `main` на момент составления отчёта.

## BUG-001: Приложение падает при чтении настроек с неизвестным значением интервала

| Поле | Значение |
|---|---|
| **Severity** | Critical |
| **Priority** | P0 |
| **Статус** | Open |
| **Компонент** | `data/mapper/NewsMapper.kt` → `Int.toInterval()`, используется в `SettingsRepositoryImpl` |
| **Regression test** | `NewsMapperTest.BUG-001: toInterval throws on unknown minute value instead of falling back` |
| **Related test case** | TC-082 |

### Описание
Функция `Int.toInterval()` ищет соответствие числа минут одному из значений enum
`Interval` и **выбрасывает `NoSuchElementException`**, если совпадения нет — вместо
того, чтобы вернуть `null` или дефолтное значение.

`SettingsRepositoryImpl` читает интервал из DataStore следующим образом:

```kotlin
preferences[intervalKey]?.toInterval() ?: Settings.DEFAULT_INTERVAL
```

Elvis-оператор (`?:`) здесь **не защищает** от падения, потому что он срабатывает
только если `preferences[intervalKey]` равен `null`. Если значение в DataStore
присутствует, но не входит в текущий список `Interval.entries` (например, осталось
от версии приложения, где такой интервал существовал, а потом был удалён), метод
`toInterval()` бросает исключение, которое ничем не перехватывается — то есть **прямо
до Elvis-оператора дело не доходит**.

### Шаги воспроизведения
1. Установить и открыть приложение, выбрать любой интервал обновления в настройках
   (значение сохраняется в DataStore как число минут).
2. Обновить приложение до версии, в которой список допустимых интервалов в `Interval`
   изменился (удалён вариант, который был выбран на шаге 1) **— либо** напрямую
   записать в DataStore произвольное число минут, не входящее в `Interval.entries`
   (например, через adb: `run-as ... sqlite3 ...` для DataStore Preferences, либо
   программно в тесте, как в `NewsMapperTest`).
3. Открыть экран настроек / инициировать чтение `Settings`.

### Фактический результат
`NoSuchElementException` — приложение крашится при каждой попытке прочитать настройки.

### Ожидаемый результат
Метод должен либо возвращать `null` для незнакомых значений (тогда Elvis-оператор в
`SettingsRepositoryImpl` сработает и вернёт `Settings.DEFAULT_INTERVAL`), либо явно
обрабатывать `NoSuchElementException` на уровне репозитория.

### Предлагаемый фикс
```kotlin
fun Int.toInterval(): Interval? = Interval.entries.find { it.minutes == this }
```
и в `SettingsRepositoryImpl` оставить как есть (Elvis-оператор тогда уже сработает
корректно).

### Влияние
Любой пользователь, ранее выбравший интервал, который перестал существовать в новой
версии приложения, получает **краш при каждом запуске** — приложение становится
полностью неработоспособным без переустановки.

## BUG-002: Дата публикации статьи парсится в локальном часовом поясе вместо UTC

| Поле | Значение |
|---|---|
| **Severity** | Medium |
| **Priority** | P1 |
| **Статус** | Open |
| **Компонент** | `data/mapper/NewsMapper.kt` → функция парсинга `publishedAt` |
| **Regression test** | `NewsMapperTest.BUG-002 - publishedAt is parsed using the local timezone even though the API returns UTC` |
| **Related test case** | TC-085 |

### Описание
NewsAPI отдаёт `publishedAt` в формате ISO 8601 с суффиксом `Z`, обозначающим UTC
(например, `"2024-05-01T10:15:00Z"`). В коде используется:

```kotlin
SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss'Z'", Locale.getDefault())
```

Символ `'Z'` **в одинарных кавычках** трактуется `SimpleDateFormat` как **буквальный
символ** "Z" в строке, а не как токен часового пояса. Поскольку `TimeZone` для
`SimpleDateFormat` явно не задан, используется `TimeZone.getDefault()` — то есть
часовой пояс устройства пользователя. В результате время интерпретируется как
**локальное**, хотя по факту оно UTC.

### Шаги воспроизведения
1. Установить на устройстве/эмуляторе часовой пояс, отличный от UTC (например,
   `Europe/Moscow`, UTC+3).
2. Получить от API статью с `publishedAt = "2024-05-01T10:15:00Z"`.
3. Сравнить полученный `timestamp` (мс) с эталонным UTC-значением
   (`Instant.parse("2024-05-01T10:15:00Z").toEpochMilli()`).

### Фактический результат
Значение timestamp смещено на величину UTC-офсета устройства (в примере с
`Europe/Moscow` — на 3 часа вперёд относительно реального времени публикации).

### Ожидаемый результат
Timestamp должен точно соответствовать UTC-времени, присланному сервером,
независимо от часового пояса устройства.

### Влияние
- Некорректно отображаемая на карточке статьи дата/время публикации.
- Возможное нарушение сортировки статей (`ORDER BY publishedAt DESC`), если статьи
  с разницей во времени публикации меньше офсета часового пояса пользователя
  "перепутываются" местами.
- Баг **тихий** (не приводит к крашу), поэтому мог бы долго оставаться незамеченным
  без целевого теста, сравнивающего результат с независимо посчитанным эталоном.

### Предлагаемый фикс
```kotlin
val formatter = SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss'Z'", Locale.getDefault()).apply {
    timeZone = TimeZone.getTimeZone("UTC")
}
```
Либо, что предпочтительнее в современном коде, — заменить `SimpleDateFormat` на
`java.time.Instant.parse(...)`, что заодно устраняет и BUG-003.

## BUG-003: Общий (не thread-safe) экземпляр `SimpleDateFormat`

| Поле | Значение |
|---|---|
| **Severity** | Medium |
| **Priority** | P2 |
| **Статус** | Open |
| **Компонент** | `presentation/utils/DateFormatter.kt` |
| **Regression test** | Не покрыт детерминированным unit-тестом (см. секцию "Почему не покрыто тестом" ниже) |
| **Related test case** | — |

### Описание
```kotlin
private val formatter = SimpleDateFormat.getDateInstance(DateFormat.SHORT)

fun Long.formatDate(): String {
    return formatter.format(this)
}
```

`formatter` объявлен как **top-level `private val`**, то есть единственный на весь
процесс экземпляр, разделяемый между всеми вызовами `formatDate()`. `SimpleDateFormat`
**официально не thread-safe** (задокументировано в Javadoc класса) — его внутреннее
состояние (в частности, используемый `Calendar`) мутируется при каждом вызове
`format()`.

Если `formatDate()` будет вызван параллельно из нескольких потоков (например, при
одновременном рендеринге списка статей с фоновым обновлением через WorkManager,
которое тоже может форматировать даты для уведомлений), возможны:
- некорректно отформатированные строки дат;
- в редких случаях — `ArrayIndexOutOfBoundsException` / `NumberFormatException`
  внутри `SimpleDateFormat` из-за гонки за внутренним состоянием.

### Шаги воспроизведения (концептуально)
1. Одновременно из двух и более потоков вызвать `someTimestamp.formatDate()`
   большое количество раз (тысячи итераций) с разными значениями `Long`.
2. При достаточном числе итераций и параллелизме — часть вызовов вернёт неверно
   отформатированную строку либо приложение упадёт с внутренним исключением
   `SimpleDateFormat`.

### Почему не покрыто детерминированным unit-тестом
Это классическая **race condition** — она не воспроизводится стабильно на каждом
прогоне, а зависит от таймингов планировщика потоков JVM. Stress-тест (например,
запуск 100+ потоков с `CountDownLatch` в цикле в течение нескольких секунд) может
поймать проблему статистически, но такой тест был бы **flaky** (иногда проходит,
иногда падает) и не подходит для стабильного CI-гейта — поэтому он сознательно не
включён в автоматический набор. Правильный способ "закрыть" этот баг — не тест, а
фикс архитектуры (см. ниже), после чего проблема устраняется по конструкции.

### Предлагаемый фикс
Использовать `ThreadLocal<SimpleDateFormat>` (классический паттерн для legacy Java
API) **или**, что предпочтительнее в Kotlin/Android-коде, перейти на
`java.time.format.DateTimeFormatter`, который immutable и thread-safe по дизайну:

```kotlin
private val formatter = DateTimeFormatter.ofLocalizedDate(FormatStyle.SHORT)

fun Long.formatDate(): String =
    Instant.ofEpochMilli(this).atZone(ZoneId.systemDefault()).format(formatter)
```

### Влияние
Низкая вероятность проявления при типичном сценарии использования (UI обычно
однопоточный), но риск растёт при активном использовании фонового обновления и
уведомлений одновременно с открытым UI. Проявляется непредсказуемо, что делает такие
баги особенно дорогими в продакшене — тяжело воспроизвести и продиагностировать
по одному крэш-репорту.

## BUG-004: Потенциальная потеря данных из-за `fallbackToDestructiveMigration`

| Поле | Значение |
|---|---|
| **Severity** | Low |
| **Priority** | P3 |
| **Статус** | Open |
| **Компонент** | `di/DataModule.kt`, конфигурация `Room.databaseBuilder(...)` |
| **Regression test** | Архитектурный риск, не воспроизводится unit-тестом (см. ниже) |
| **Related test case** | — |

### Описание
```kotlin
Room.databaseBuilder(...)
    ...
    .fallbackToDestructiveMigration(true)
    .build()
```

Эта настройка означает: если версия схемы БД на устройстве не совпадает с текущей
и **явная миграция для этого перехода не определена**, Room **полностью удаляет и
пересоздаёт базу данных** — без предупреждения пользователя и без возможности отмены.

Для pet-проекта на этапе разработки это осознанно удобно (не нужно писать миграции на
каждое изменение схемы). Но это же означает, что при выпуске обновления, меняющего
схему БД (например, добавление колонки в `ArticleDbModel`), **все локальные подписки
и сохранённые статьи пользователя будут молча удалены** при первом запуске новой
версии.

### Шаги воспроизведения (концептуально)
1. Установить текущую версию приложения, добавить несколько подписок.
2. Выпустить версию с изменённой схемой БД (например, новое поле в Entity) без
   написания `Migration`.
3. Обновить приложение до новой версии.

### Фактический результат
Все локальные подписки и статьи пользователя удаляются без предупреждения.

### Ожидаемый результат (для production-приложения)
Либо: явные `Migration`-объекты для каждого изменения схемы, сохраняющие данные
пользователя. Либо, как минимум: явный экран/диалог, предупреждающий пользователя
о потере локальных данных при неизбежном destructive-обновлении.

### Почему это не покрыто unit-тестом
Проверка "не произошло ли молчаливое удаление БД при миграции" требует реального
сценария апгрейда версии схемы (создание БД со старой схемой, попытка открыть её
новым `RoomDatabase`), что выходит за рамки модульного теста и ближе к отдельному
"migration test" с использованием `MigrationTestHelper` — целесообразно завести
как отдельную задачу, если проект продолжит развиваться в сторону production.

### Влияние
Для pet/demo-проекта — минимальное (пользователь может просто заново подписаться).
Для гипотетического production-сценария — потенциальная потеря пользовательских
данных без возможности восстановления, что критично с точки зрения UX и доверия.

### Рекомендация
Задокументировано как **осознанный технический долг** с низким приоритетом,
подходящий кандидат для реальных `Room Migration` при дальнейшем развитии проекта.

## BUG-005: Обманчивый null-safe fallback при парсинге даты — на деле бросает исключение

| Поле | Значение |
|---|---|
| **Severity** | Medium |
| **Priority** | P1 |
| **Статус** | Open |
| **Компонент** | `data/mapper/NewsMapper.kt` → `String.toTimestamp()` |
| **Regression test** | `NewsMapperTest.BUG-005 - toDbModels throws ParseException for a malformed publishedAt instead of falling back`, `NewsRepositoryImplTest.BUG-005 consequence - a single malformed article discards the whole topic batch, not just itself` |
| **Related test case** | — (см. секцию 5 `TEST_CASES.md`, аналогично TC-084/TC-085) |

### Как был найден
В отличие от остальных багов этого отчёта, найденных через первичное код-ревью,
этот баг обнаружился уже **в процессе написания unit-теста** для соседнего сценария
(парсинг некорректной даты). Хороший пример того, зачем нужны тесты граничных
случаев: код выглядел абсолютно безопасным при чтении, но фактическое поведение
API оказалось другим.

### Описание
```kotlin
private fun String.toTimestamp(): Long {
    val dateFormatter = SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss'Z'", Locale.getDefault())
    return dateFormatter.parse(this)?.time ?: System.currentTimeMillis()
}
```

Конструкция `dateFormatter.parse(this)?.time ?: System.currentTimeMillis()` **выглядит**
как безопасный fallback на текущее время при нераспознанной строке. Но однопараметрический
`SimpleDateFormat.parse(String)` **никогда не возвращает `null`** — при нераспознанной
строке он бросает `ParseException`. То есть `?.time` и `?:` здесь — мёртвый код,
защищающий от ситуации, которая физически не может произойти через эту перегрузку метода;
реальная же ошибка (невалидная строка от API) не перехватывается вообще.

### Шаги воспроизведения
1. Получить от API (или подставить в тесте) статью с `publishedAt`, не соответствующим
   формату `yyyy-MM-dd'T'HH:mm:ss'Z'`, например `"not-a-date"`.
2. Вызвать `NewsResponseDto.toDbModels(topic)`.

### Фактический результат
Бросается `java.text.ParseException`, которая **не перехватывается на уровне маппера**.

### Что происходит дальше по стеку вызовов (важно для оценки impact)
`toDbModels()` вызывается внутри `NewsRepositoryImpl.loadArticles()`, где есть общий
`try { ... } catch (e: Exception) { ...; listOf() }`. Это исключение действительно
перехватывается — то есть **краш приложения не происходит**. Но ценой этого является
то, что **вся партия статей по теме отбрасывается целиком**, включая корректные статьи,
соседствующие в том же ответе API с одной "плохой" датой. Это подтверждено
интеграционным тестом на уровне репозитория.

### Ожидаемый результат
Ошибка парсинга даты **одной** статьи не должна приводить к потере остальных, валидных
статей в том же ответе API. Fallback на текущее время (как и предполагалось изначальным
автором кода, судя по `?:`) должен реально работать для конкретной "битой" статьи.

### Предлагаемый фикс
```kotlin
private fun String.toTimestamp(): Long {
    val dateFormatter = SimpleDateFormat("yyyy-MM-dd'T'HH:mm:ss'Z'", Locale.getDefault()).apply {
        timeZone = TimeZone.getTimeZone("UTC") // заодно фиксит BUG-002
    }
    return try {
        dateFormatter.parse(this)?.time ?: System.currentTimeMillis()
    } catch (e: ParseException) {
        System.currentTimeMillis()
    }
}
```
и, чтобы одна невалидная статья не роняла всю партию — маппить статьи в
`toDbModels()` через `mapNotNull` с try-catch на уровне отдельной статьи, а не
полагаться на то, что вся операция целиком защищена одним внешним catch.

### Влияние
Пользователь может недосчитаться новых статей в ленте после обновления, если в ответе
API среди прочих оказалась хотя бы одна статья с нестандартной датой — без какой-либо
видимой ошибки или сообщения. Особенно неприятно в сочетании с фоновым обновлением
(`RefreshDataWorker`): пользователь просто видит "новых статей нет" там, где они
на самом деле были.
