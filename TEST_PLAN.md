# Test Plan — NewsAppDemo

## 1. Введение

### 1.1 Цель документа
Данный тест-план описывает подход, объём и стратегию тестирования Android-приложения
**NewsAppDemo** — клиента для агрегации новостей по темам подписки с использованием
[NewsAPI](https://newsapi.org/).

### 1.2 Описание приложения
Приложение позволяет пользователю:
- подписываться на новостные темы (ключевые слова) и отписываться от них;
- просматривать ленту статей по выбранным подпискам;
- настраивать язык новостей, интервал фонового обновления, использование только
  Wi-Fi для загрузки и push-уведомления о новых статьях;
- получать статьи в фоне даже при закрытом приложении (WorkManager).

### 1.3 Архитектура (важно для тестирования)
Приложение построено по Clean Architecture с разделением на слои:

| Слой | Компоненты | Как тестируется |
|---|---|---|
| **presentation** | Jetpack Compose UI, ViewModel (MVVM) | Compose UI-тесты, unit-тесты ViewModel |
| **domain** | Use Case'ы, доменные entity, интерфейсы репозиториев | Unit-тесты с моками репозиториев |
| **data** | Repository-реализации, Room DAO, Retrofit API, мапперы | Unit-тесты мапперов, интеграционные тесты (Robolectric + in-memory Room), тесты репозитория с моками Dao/Api |

Такое разделение даёт возможность тестировать бизнес-логику изолированно от Android
framework (быстрые JVM-тесты) и покрывать критичные интеграционные сценарии отдельно.

## 2. Объём тестирования

### 2.1 Что тестируется (in scope)
- Маппинг данных между слоями (DTO → DB model → Domain entity) — `NewsMapper`, `SettingsMapper`
- Бизнес-логика Use Case'ов (domain layer)
- Логика ViewModel'ей (управление состоянием экрана, обработка команд пользователя)
- Работа с локальной БД (Room): подписки, статьи, каскадное удаление, foreign key
- Работа репозиториев с сетевым слоем (обработка ошибок сети, дедупликация статей)
- Ключевые пользовательские сценарии на экранах Subscriptions и Settings (Compose UI)
- Запуск приложения без падений (smoke-тест)
- Регресс на найденные баги (см. `BUG_REPORTS.md`)

### 2.2 Что не тестируется (out of scope) и почему
| Область | Причина исключения |
|---|---|
| Реальные сетевые запросы к NewsAPI | Требует реального API-ключа и стабильно доступен извне; заменяется моками/MockWebServer |
| WorkManager: реальное периодическое выполнение по расписанию системы | WorkManager тестируется через `WorkManagerTestInitHelper` в рамках unit-тестов конфигурации; полноценный e2e прогон по таймеру ОС нецелесообразен для CI |
| Push-уведомления (реальная доставка через систему) | Вне контроля приложения; тестируется только вызов API `NotificationManager` |
| Локализация полного объёма строк (все языки) | Проверяются лишь ключевые экраны на английском как smoke; полноценный l10n QA — отдельная задача |
| Нагрузочное/производительное тестирование | Не в фокусе pet-проекта; возможное направление для дальнейшего развития |

## 3. Тестовые уровни и инструменты

| Уровень | Инструменты | Где выполняется |
|---|---|---|
| Unit-тесты (JVM) | JUnit4, MockK, kotlinx-coroutines-test, Turbine, Truth | Локально / CI, без эмулятора |
| Интеграционные тесты (JVM + Robolectric) | Robolectric, Room (in-memory) | Локально / CI, без эмулятора |
| UI-тесты (Compose) | Espresso, Compose UI Testing (`ComposeTestRule`), MockK | CI, Android-эмулятор (API 33) |
| Smoke-тест | AndroidX Test, ActivityScenario | CI, Android-эмулятор |
| Статический анализ / ручное код-ревью и тест-дизайн | — | Найдены и задокументированы 5 багов (см. `BUG_REPORTS.md`) |

### Почему не всё гоняется через реальный эмулятор
DAO-тесты выполняются через **Robolectric** (эмулирует Android framework в JVM) —
это даёт реальную работу с SQLite/Room, но выполняется в разы быстрее эмулятора и не
требует его поднятия в CI на каждый unit-тест. Полноценный эмулятор используется только
там, где действительно нужен реальный рендеринг Compose UI и Instrumentation — то есть
для UI-тестов экранов и smoke-теста.

## 4. Стратегия по типам тестов

### 4.1 Unit-тесты мапперов (data layer)
Мапперы — точка наибольшего риска "тихих" багов (неверная трансформация данных без
исключения). Покрыты позитивные и граничные кейсы, включая специально
задокументированные баги (см. `NewsMapperTest`, `SettingsMapperTest`).

### 4.2 Unit-тесты Use Case (domain layer)
Каждый Use Case тестируется изолированно с моками репозиториев через MockK.
Проверяется: корректная передача параметров, использование текущих Settings,
обработка пустых/граничных данных.

### 4.3 Unit-тесты ViewModel (presentation layer)
Используется `MainDispatcherRule` для подмены `Dispatchers.Main` и `Turbine` для
тестирования потоков состояния (`StateFlow`). Все зависимости (Use Case) замоканы —
ViewModel тестируется в полной изоляции от Android framework.

### 4.4 Интеграционные тесты Room (Robolectric)
`NewsDaoTest` работает с реальной in-memory базой данных и реальными SQL-запросами,
сгенерированными Room. Это единственный способ достоверно проверить:
- ON CONFLICT / уникальные ограничения;
- поведение внешних ключей (foreign key constraints) и каскадное удаление;
- фактический порядок сортировки (`ORDER BY`).

### 4.5 UI-тесты (Compose)
Тестируются ключевые пользовательские сценарии: ввод темы подписки, добавление/
удаление подписки, переключение настроек, навигация между экранами. ViewModel
создаётся напрямую с замоканными Use Case (без Hilt-тестового рантайма), чтобы
тесты были быстрыми и не зависели от DI-графа.

### 4.6 Приоритизация тест-кейсов
Тест-кейсы в `TEST_CASES.md` размечены по приоритету:
- **P0 (Critical)** — сценарии, при провале которых приложение падает или теряет
  пользовательские данные;
- **P1 (High)** — основной happy path пользовательских сценариев;
- **P2 (Medium)** — edge-cases, обработка ошибок, второстепенные настройки.

## 5. Окружение и данные

- **Инструменты сборки:** Gradle, AGP, Kotlin 2.x, KSP
- **CI:** GitHub Actions (workflow `.github/workflows/android-firebase-testlab.yml`)
  - job `test-and-build` — unit-тесты, отчёт покрытия JaCoCo, сборка APK
  - job `instrumented-tests` — Compose UI-тесты и smoke-тест на Android-эмуляторе
    (API 33, x86_64, google_apis, профиль Pixel 6) — бесплатный, без GCP-биллинга
  - job `firebase-test-lab` — опциональный прогон на реальной матрице устройств
    (требует настройки GCP-биллинга, выключен по умолчанию)
- **Тестовые данные:** генерируются в самих тестах (fixtures внутри тест-классов),
  внешние тестовые данные/сиды не требуются
- **Покрытие кода:** JaCoCo, HTML+XML отчёт публикуется как CI-артефакт

## 6. Критерии выхода (Exit Criteria)

- Все тесты уровня P0 и P1 проходят успешно
- Нет открытых багов с критичностью Critical без фикса или явного waiver
- CI полностью зелёный (unit + instrumented jobs)
- Отчёт JaCoCo сгенерирован и приложен к сборке

## 7. Риски

| Риск | Митигация |
|---|---|
| Ограничение бесплатного тарифа NewsAPI (rate limit) при ручном тестировании | UI/unit-тесты не делают реальных сетевых вызовов |
| Нестабильность (flakiness) эмулятора в CI | `disable-animations: true`, использование `UnconfinedTestDispatcher`/`Turbine` вместо `Thread.sleep` |
| Расхождение поведения Robolectric и реального устройства | Критичные UI-сценарии дополнительно проверяются на реальном эмуляторе (job `instrumented-tests`) |
